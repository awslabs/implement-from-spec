Java (Spring Boot services, AWS Lambda functions, shared libraries), built with Maven or Gradle. Review across seven dimensions: correctness, design, patterns, extensibility, security, maintainability, readability. Look hardest at:
- Behaviour versus the specification items and the plan's Global constraints: names, paths, status codes, fields and properties exactly as stated; anything missing, stubbed, hard-coded to the happy path or not wired into the code that runs. Where the project keeps a specification tree, a business-behaviour change without the matching SPEC, TC and coverage-matrix update is a Blocker, and every new test names its item or TC-xxx
- Code that silently answers an open question from the project's open-questions list
- Layering: controllers stay thin; services never do their own file or network I/O outside the adapter layer
- Records for value types, no Lombok, constructor injection only, tunables on the single @ConfigurationProperties bean
- Null handling at boundaries, Optional misuse, resource leaks, unclosed SDK response streams, swallowed InterruptedException, catch-all handlers, fallbacks that hide logic bugs
- Shared mutable state across requests or Lambda invocations, executor sizing, blocking calls without a timeout
- AWS SDK: any SDK for Java 1.x use (com.amazonaws:aws-java-sdk-*; the Lambda runtime and event libraries and the AWS Encryption SDK share the group and are not 1.x); a client built per call or per invocation instead of once and reused; no apiCallTimeout or apiCallAttemptTimeout; missing pagination; retries that repeat a non-idempotent write
- Lambda: a handler that is not idempotent on a duplicate event; event or user data kept in static state; for SnapStart, unique values or entropy created during initialization, or EnvironmentVariableCredentialsProvider pinned
- Injection: untrusted input reaching SQL or JPQL text, an OS command, an LDAP, XPath or NoSQL query, an expression language or template, a script engine, a JNDI name, an HTTP header, a class name or a regular expression; output not encoded for where it is rendered; a CSV or spreadsheet cell that can start with a formula character; caller text in a LIKE pattern with % and _ unescaped
- Deserialisation, data binding and XML: Java serialisation or type handling that lets untrusted data choose the class (Jackson, YAML, XStream); request data bound straight onto entities; XML parsers, transformers and schema factories that leave DTDs, external entities or extension functions on
- Cryptography, randomness, TLS and secrets: a non-secure random for tokens; ECB, a reused GCM nonce, MD5 or SHA-1 for security; passwords under a fast digest; comparisons of secrets that are not constant-time; a trust-all TrustManager or HostnameVerifier; secrets in source, defaults, logs or snapshots
- Authentication, sessions, tokens and authorisation: a token accepted without checking signature, issuer, audience and expiry; session fixation and cookie attributes; an object reached by an ID from the request with no ownership or tenant check; identity taken from the request instead of the security context; routes not denied by default; method security relied on but not enabled
- Web surface and Spring configuration: CSRF switched off where browsers send credentials; broad CORS with credentials; open redirects; file uploads; forwarded headers trusted from any source; stack traces or SQL in error bodies; actuator and development endpoints exposed
- Files, input, outbound requests, logs and failure: jakarta.validation on every DTO field; path traversal and archive extraction; temporary files; unbounded reads and decompression; a caller-chosen URL or host reaching an HTTP client; a costly operation (an export, a report, a bulk read) with no per-caller limit; line breaks and sensitive data in logs; no audit record of who read or exported personal data; a check that fails open
- AWS SDK and Lambda security: credentials in code; presigned URLs; S3 event keys used without URL-decoding; PartiQL built by concatenation; SNS messages accepted without signature verification; KMS calls without an encryption context; secrets kept in a SnapStart snapshot
- Dependencies and build files: new dependencies or plugins not named in the approved plan, unpinned, dynamic or snapshot versions, a database, ORM, broker or cloud SDK added without approval; a managed or forced version that lowers a transitive dependency; a plain-HTTP or new repository; a weakened checksum or signature check; credentials in a build file
- Known vulnerabilities: a library API used in the way a known CVE exploits, or a dependency version you believe is vulnerable: name the artifact and say "verify against the advisory data" rather than asserting, because your knowledge of advisories is dated and the review's dependency audit checks versions
- Tests that would pass even if the feature were broken; tests that reach the network
- Stale Javadoc and comments next to changed lines
- Temporal compatibility: old and new versions running side by side, migration or backfill order, replay of events written before the change, rollback after the new version wrote data, partial deployment
- A specification item or test case edited by this change that no approved plan item or amendment covers (an unapproved requirement change)
- For every finding, the evidence as a causal argument: what triggers the defect, the path it takes (file:line steps) and the wrong result; mark a defect that exists on the base independently of this change "pre-existing"
- Library behaviour you are not sure of (Spring, the AWS SDK, Jackson): say "verify against the docs" rather than asserting
- Precedence: the repository rules, the specification items and the approved plan override these defaults; a deviation the project prescribes is not a finding, except that no rule or plan line waives a security hazard
