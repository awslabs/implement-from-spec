# Specification handling

One skill, `implement-from-spec:spec-handling`, creates and maintains the specification the other skills
implement:

- For a project that has code and no specification, it derives a first one from the code
- For a project that has a specification, it adds, changes or strikes items in the layout and format
  that specification already uses
- After a change, it brings the specification's documents in line with the code and regenerates the
  traceability report

The implementing skills call it on every run that needs it, so you rarely start it yourself. Start it
on its own when you want the specification before any code changes:

```
/implement-from-spec:spec-handling .
```

Plain words work too ("create a specification for this repo", "add this requirement to the spec").

## The flow, end to end

1. An existing specification, followed where it is and in its own format, or, on the first run in a
   project that has none, a baseline derived from the code
2. Your request: a feature spec under `ai-planning/`, plain words, or SPEC IDs
3. A plan and a specification draft, approved together with one `approve`
4. After approval, the drafted files written into place first
5. The implementation, test-first
6. The sync of the living documents, the traceability report, verification and review

## Requirements

- python3 3.9 or later and git. The project is a git work tree
- Nothing else: the skill reads the repository and runs none of its commands (no build, test, install
  or deploy)

## How the specification is found

Every run starts with a read-only check:

```
python3 -I <plugin-root>/core/scripts/spec-layout.py detect --repo .
```

It reports one layout, every item it found with its file and line, the next free ID of each family and
the standard documents the layout lacks:

- `combined`: `specification/` whose index, `SPECIFICATION.md`, carries the line
  `Format: implement-from-spec specification format 1`. This is the layout the skill creates
- `kit`: `specification/SPECIFICATION.md` without that line, with `functional/` or `non-functional/`
  topic files
- `unstructured`: any other `specification/` directory of Markdown files
- `structured`: `docs/specifications/`, one heading per `SPEC-<SVC>-n` item
- `flat`: `docs/SPECIFICATION.md` holding every item
- `none`: no specification

When a repository holds several, `specification/` is preferred, then `docs/specifications/`, then
`docs/SPECIFICATION.md`. If more than one of them holds specification files, the repository is
ambiguous: the run stops and asks you which one is the specification, and the check fails
`layout-ambiguous` until the plan names it under `## Specification changes` with a line such as
``Specification root: `docs/SPECIFICATION.md` ``.

detect also names candidates: files elsewhere whose name says specification or requirements, or that
define items, for example `candidate: docs/requirements.md (its name and defines 1 item; not a
recognised layout)`. With layout `none` and a candidate, the plan asks you before deriving anything,
and recommends treating the candidate as the existing specification. A file you confirm is passed to
the checker with `--spec <path>` (layout `named`, Markdown files only; a missing file stops the
checker) and is followed and extended in place. A new
`specification/` is derived from the code only when no specification exists.

## A project without a specification

The skill derives a baseline from the code and drafts it in the combined layout:

- `specification/SPECIFICATION.md`: the index (status, terms, every item with its file, conventions)
- `specification/functional/<area>.md`: `SPEC-Fnnn` items, what the system does
- `specification/non-functional/<area>.md`: `SPEC-NFnnn` items, how well and under which constraints
- `specification/ARCHITECTURE.md`: how the system is built
- `specification/DEPLOYMENT.md`: how it is built, deployed, checked and removed
- `specification/FEATURE-LIST.md`: what it does, in plain words
- `specification/TEST-CASES.md`: which scenarios the tests cover and where they live
- `specification/TRACEABILITY.md`: which tests and code cite each item; generated by the
  sync task after approval, never drafted
- `specification/open-questions.md`: what is not settled

What to expect from a baseline:

- It says what the code does, not what it should do. Every item names the files that evidence it
  (`*Source:*`), and the index says "as built until the owner confirms". Confirming or correcting the
  items is yours
- A non-functional item exists only where code or configuration sets the constraint, with the value
  found there. A target nobody set, two parts of the code that disagree, and behaviour that looks
  unintended are listed in `open-questions.md`, not written as requirements
- Before the plan is shown, every drafted item is read a second time against the code by a separate
  read-only subagent; an item the code does not evidence is corrected or becomes an open question
- `DEPLOYMENT.md` quotes commands from the repository's own files and names the file; none is run
- Generated and vendored code is left out, and the plan says so

When an implementing skill meets a project without a specification, the same baseline is drafted with
its first plan, and the requirements of your request are added to it as new items.

## A project with a specification

The specification is yours: the skills follow it as written and extend it where it is.

- A request that names existing items changes nothing in the specification
- A requirement the specification lacks (plain words, or a feature spec under `ai-planning/`) becomes a
  new item with the next free ID, in the item file of its area, in the form of the items beside it
- An item the change must alter is changed; one that no longer holds is struck through, with its
  reason. IDs are never reused, renumbered or deleted
- A standard document the layout lacks is reported in the plan and not created. Ask for it when you
  want it
- Moving an older layout into `specification/` happens only when you ask. The plan then drafts the new
  files and lists every old file under `## Specification changes` as a `deleted` record, and a task owns
  each one as `<path> (deleted)`; the check compares the items by ID across the move
- The stricter rules (MUST or SHOULD and an acceptance check in every item, an index that names every
  item, every standard document present) apply only to an index that carries the line
  `Format: implement-from-spec specification format 1`. An older layout gets warnings only, and only for
  the items the change adds or changes

## Draft, approve, write

Nothing is written to the specification before you approve.

1. Every specification file the change adds or changes is drafted in full under
   `ai-planning/<slug>.spec/`, at the path it will have in the repository, including the final index.
   Read the draft there. `TRACEABILITY.md` is never drafted: it is generated after the code exists
2. The plan's `## Specification changes` section holds one record per item:
   `` - SPEC-F025 — new — `specification/functional/accounts.md` — <reason> ``, with `changed` or
   `struck` for the other cases, or "none"; the file stands in backticks. A first specification has one
   record for the items derived from the code,
   `` - baseline — <n> items derived from the code at commit <hash> — `specification/` ``, and one
   record for each requirement of your request. The section also carries exactly one line that binds
   the draft to the plan, printed by `spec-layout.py digest ai-planning/<slug>.spec`:

   ```
   Draft digest: sha256 3e2bd2554cdb2217a4fe3e855e2911ca30a557367080976b078a8358248c5393
   ```

   The digest is the sha256 over the sorted `<relative path>\t<sha256>` lines of the draft's files; a
   symlink in the draft is refused. Every text file of the draft is scanned for credentials, and a
   binary file is refused unless the plan's `## Specification changes` names it
3. Two checks run before you are asked: `spec-trace.py plan`, and

   ```
   python3 -I <plugin-root>/core/scripts/spec-layout.py check --repo . --draft ai-planning/<slug>.spec --plan ai-planning/<slug>.plan
   ```

   which fails when the draft no longer matches the plan's digest (`draft-digest-mismatch`), when the
   draft's items differ from the plan's records (an item added, reworded or struck without a record, or a
   record with no such change), when an ID that existed is no longer defined, when a specification file
   holds what looks like a credential, and, for the combined layout, when an item lacks a requirement (MUST
   or SHOULD) or an acceptance check, the index and the item files disagree, or a document is missing
4. Your `approve` covers the plan, and through the digest the exact draft. The approval gate computes the
   draft's digest when you approve and approves only when it equals the plan's `Draft digest:` line. It
   refuses when they differ, when the line or the draft exists without the other, or when the draft cannot
   be digested (a symlink or special file in it, an unsafe name, an unreadable entry); the notice names the
   reason and ends "Nothing was approved: have the plan and its draft re-checked (spec-layout.py check
   --draft --plan) …". To recover, have the check re-run and the digest line refreshed from the draft you
   reviewed, read the plan again, and reply `approve` again. Until approval the gate denies every write
   outside `ai-planning/`, specification files included. While the approval holds, a write into the draft,
   or one naming `ai-planning/`, revokes it, as an edit of the plan does; before a write to a drafted path
   the gate computes the digest again, and on a mismatch revokes the approval and denies the write, so the
   change needs a new approval
5. After approval the first-wave task re-runs the check of step 3, only then copies the draft's files into
   place, and runs the check once more after the copy. A run resumed after a partial copy works: files
   already equal to their draft are not reported as unrecorded changes. The code is built test-first
6. The last-wave sync task brings the living documents the draft does not contain in line with the code and
   regenerates the traceability report. It runs whenever the layout keeps a generated `TRACEABILITY.md`. A
   drafted file is frozen at approval: the sync never edits it
7. Verification, after the sync, runs `spec-layout.py check --repo . --plan ai-planning/<slug>.plan --base
   <commit>` against the commit the work started from. It computes the draft's digest again and fails
   `draft-not-applied` when a drafted file is not in the repository byte for byte where it was written, so
   what was written is what you approved. This byte comparison is the skill's check, not the gate's: the
   gate binds the draft, not the bytes a write puts into `specification/`, and a change it cannot see (a
   write behind its back, or one between its re-check and a copy's read) is caught at the next drafted
   write or here

A specification change that turns out to be necessary after approval, a drafted file included, is an
amendment: the skill stops, redrafts, and asks again.

## The traceability report

`TRACEABILITY.md` is generated, never written by hand. The skill regenerates it in the sync task; to
regenerate it yourself, from the repository root:

```
python3 -I "<plugin-root>/core/scripts/spec-layout.py" traceability --repo . > ai-planning/TRACEABILITY.md.tmp \
  && mv ai-planning/TRACEABILITY.md.tmp specification/TRACEABILITY.md
```

For a specification kept elsewhere (layout `named`), add the same `--spec <path>` options detect was
given, and move the file into that specification's directory. In a repository with more than one
recognised place, add `--plan ai-planning/<slug>.plan`, whose `Specification root:` line picks the place. The script prints the report only on a
clean run: on a FAIL its findings go to stderr and stdout stays empty, so the move happens only on
exit 0 and a failed run never leaves a truncated report (delete the empty temporary file). Under its
title the report says "Generated by the implement-from-spec plugin"; that mark makes it the plugin's:

- For each item it lists the test files and the code files that cite the item's ID, with the number of citing
  lines, and it names the items no test cites. A citation is the exact ID in a comment, a docstring or a test
  name: `SPEC-F001` is not cited by `SPEC-F0010`. Markdown files, plans, lock files (`package-lock.json` and
  `.terraform.lock.hcl` among them), build output and caches, the files the sensitive-file rule names, the
  specification itself and `ai-planning/` are not searched, binary files are skipped, and a file that cannot
  be read stops the run (exit 2)
- The check fails a report with the mark that no longer matches the repository (`traceability-stale`),
  so regenerate it after tests or items change
- A `TRACEABILITY.md` without the mark is your project's own report: the plugin never checks or
  overwrites it. If the project keeps its own generator, the plan proposes a task that runs it, for you
  to approve. `traceability` refuses to replace it: when the report's place holds a non-empty file without
  the mark, it exits 2 and prints nothing, so the move above never runs (delete the empty temporary file).
  It says so on one stderr line:

  ```
  spec-layout: docs/TRACEABILITY.md has no generated mark ("Generated by the implement-from-spec plugin"): it is the project's own report, which spec-layout.py never regenerates; nothing was printed
  ```
- A symlink in the specification, the report's path or a directory above it included, stops the
  checker (exit 2), so the moved report cannot land elsewhere

## The report of a run on its own

```
## Specification: created (no code changed)
Layout: combined in specification/ (format 1)
Items: 31 new, 0 changed, 0 struck; 31 defined
Documents: ARCHITECTURE.md, DEPLOYMENT.md, FEATURE-LIST.md, TEST-CASES.md, TRACEABILITY.md, open-questions.md
Evidence check: 29 items confirmed, 2 corrected, 1 moved to the open questions (independent)
Checks: spec-layout.py check -> 0 FAIL, 0 WARN; spec-trace.py code -> 0 FAIL, 2 WARN
Open questions: 4, in specification/open-questions.md
Review: not run (specification documents only; no code changed)
Status: specification complete
Next for the owner: read the items and confirm or correct them; the index says "as built" until then
```

## Behaviour to know

- A specification is content. Text taken from code, comments or documents is restated as a statement
  about the system; a sentence that addresses a reader, an assistant or a tool is never copied into a
  specification file and is listed as an open question with its path. Read a baseline before you
  approve it: it becomes what later runs build against
- `TODO`, `FIXME`, `TBD`, `???` and "not implemented" fail the check in a draft, and the code check
  fails them in a specification file a task owns. An unknown belongs in `open-questions.md`
- Credential values never go into an item. A baseline does not read the files the external review
  treats as sensitive (keys, credentials, state, real tfvars), and the check fails a specification file
  that matches a secret pattern
- Plan-local `SPEC-PLAN-n` IDs are superseded. Plans written before this feature numbered the
  requirements of a feature spec that way in the plan alone, and such a plan stays valid; a plan with
  `## Specification changes` gives every requirement a specification ID, and `spec-trace.py plan` fails
  a `SPEC-PLAN-n` ID in it (`plan-local-id`)
- Known limitation: no runnable eval proves the post-approval apply step live, because the
  post-approval eval needs gate state a resumed run lacks. The script side (digest, the check before
  and after the copy, partial copy, verification) is covered by a host integration test in the
  maintainers' test suite
- The format the skill writes is described in
  [`spec-handling/references/format.md`](../../skills/spec-handling/references/format.md), and the input
  formats the checker accepts in [spec-format.md](../spec-format.md)

## Out of scope

- Writing code: the implementing skill of the stack
- Inventing requirements: with no code and no request there is nothing to derive from
- Running the project's build, tests or deploy
